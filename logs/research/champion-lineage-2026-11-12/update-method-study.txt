OROBENCH UPDATE METHODS STUDY
Completed 2026-11-12 using the captured public-source/race archive.

Purpose
Learn how modifications work as operational changes and assess their whole-agent performance. The earlier champion census covers 38 title versions. This study maps 18 source-adaptation comparisons, including call sites, assigned state, and same-race performance where available. Automated mapping covers 1301 added/modified direct definitions. Detailed behavioral probes cover selected mechanisms, not every agent path. No paid inference or complete-agent score evaluation was performed.

Evidence model
1. Establish exact version, source hash, release date and submission date.
2. Recover actual runtime dispatch and all terminal paths.
3. Map modification to callers, relevant inputs, state mutations, invalidation, bounds and fallback behavior.
4. Classify the intended effect on shopping decisions, question/step use, inference requests, tokens, latency or completion.
5. Compare whole versions on the same race. Record expected task coverage, included validators, score spread, cost, failed calls, runtime and field conditions.
6. Keep measured performance separate from inferred feature contribution. An individual feature requires an isolated comparison to establish its causal value.

Concrete methods

Giyu's cheaper-candidate intervention
It runs from normal checkout dispatch after fresh listing evidence and review. It requires a cheapest objective, known category/owner, affordable cheaper candidate and observed support for simple requirements. It deliberately excludes compatibility-linked items and cannot prove numeric, negative or referenced requirements by simple words. It retains cart quantity in its suggested swap, deduplicates intervention within an evidence version and allows at most two holds. It produces guidance, not an automatic cart mutation. It makes no direct model call, but holding checkout can induce an additional model turn. It does not apply universally to the forced finish path.
Learning: understand the proof domain, insertion point and attempt allowance before copying a guard.

Giyu's search transformations
The code tries compact number-unit forms, and numeric-only terms for certain lower-bound constraints. The search words broaden candidate discovery without establishing that a found item satisfies the requirement. For example, '100 w' can yield '100w' and '100'; '12 in' does not use the generic joined-unit transformation. Eligibility proof remains downstream.
Learning: separate candidate recall from acceptance. A broad search transformation must not weaken final requirement checks.

Halo's late-question handling
Before a purchase, it can spend a message previously reserved for a decline when no order procedure needs that message. It checks message, step, time and model availability, runs once, integrates any new requirement and version change, and returns control for cart reconsideration. This is conditional release of a reservation after the intended terminal action becomes known.
Learning: preserve commitments to required procedures while recovering otherwise unused information capacity.

Halo's deadline handling
Remaining time enters model-request admission and the chosen client timeout. Below 50 seconds, the model timeout is reduced to a whole five-second bucket. Below the call floor, inference is skipped. The mechanism reserves finishing time, although lower-level retries and environment operations also need inspection to determine a complete bound.
Learning: a clock affects behavior only if every relevant expensive operation uses it. A constant called 'deadline' alone is insufficient.

Cairn's observation normalization
The environment response passes through unspelled/_restore/_fold_twins before downstream evidence handling. Non-message records in several encodings are restored and flattened attributes are collected. This can improve search, questioning, property matching and cart review simultaneously because all consume the same normalized observations.
Learning: an upstream data-representation repair can improve several decision stages with one change. Preserve observation meaning and error information during normalization.

Know Thyself's ownership and compatibility
It adds item ownership, per-item question lanes, compatibility indexes and cart-count corrections. These connect requirements to the correct requested item and treat compatibility as a relationship among selections.
Learning: repair a missing state relationship rather than asking independent reviewers to rediscover it repeatedly.

YesYesYes's recovery path
It adds compatibility-code families/exclusions and recovery search after a doubtful review or decline. These additions need reserves for steps, time and inference so that recovery can end with an actionable cart.
Learning: recovery requires a specific trigger, usable evidence, a search bound and a feasible terminal action.

CURSOR's targeted fact checking
fact_check is wired into the normal reasoning path, tracks a fact_checks counter and stops after four checks. Its code targets added requirements after a cart rather than repeating an unlimited general review. Its interpretation and complete call context remain necessary to decide which scenarios it covers.
Learning: spend additional reasoning on a changed obligation with a bounded count, and identify all paths that bypass that check.

CHIDORI's layered replacement
Its Episode class composes several generations of implementation. Actual resolution selects G6B.dispatch/finish, G5A.cart_check, G3B.item_hunt/opening and E9.run. Eighteen method names have shadowed definitions. Its candidate/evidence/compatibility/basket recovery methods can do useful work between model turns.
Learning: trace Python dispatch before editing. Class organization and physical source size do not identify active behavior. Replacement methods must preserve the callers' expected state and return values.

PricePilot's disconnected additions
All original hopeoro classes/functions/settings remain AST-identical, and the original flow does not reference the extra definitions. Apparent new helper capabilities are insufficient evidence of an operational update. See pricepilot-reachability.json.
Learning: verify reachability before attributing scores to an implementation change.

Inherited weaknesses
The Halo/Cairn inference retry policy treats 402 as retryable. Isolated probes found four attempts, 34 seconds of scheduled waits, and only one increment of the logical calls counter before no_credit is set. Thus a logical call cap is not an actual HTTP-attempt cap. Source-level procedure gates can also return permission after an unusable review. These mechanisms should be assessed as failure modes even when the complete source won a title.
Learning: inherit useful mechanisms selectively. A championship does not validate every branch.

Performance conclusions
Giyu versus Cairn shared races 18-21: score changes about +3.33, -0.55, +3.90, -0.55 percentage points using means of rounded validator scores. Race 20 mean run cost fell from about $4.204 to $4.118, while the inference-call total rose. Gains were not consistent across all observed worlds.
CHIDORI versus Cairn shared races 19-21: changes about +1.11, +2.22, +5.00 points. Mean cost rose from about $3.532 to $3.833, $4.204 to $4.305, and $4.257 to $4.490 respectively. Mean sandbox wall time fell in all three comparisons. Zero/low inference failures and successful terminal behavior matter alongside token/call count.
Know Thyself versus KYO shared races 11-13: changes about +2.77, +4.44, +5.55 points. Mean sandbox duration rose in these comparisons. Better accuracy did not automatically improve speed.
KISAME versus Hello World shared races 7-9: changes about +32.78, -1.66, +11.12 points. The parent's race-9 inference failures and very short run make that result a poor isolated measure of shopping-logic improvement.
PricePilot versus hopeoro can show score differences despite identical original operational definitions. Those differences cannot be assigned to disconnected helpers.
Halo versus Know Thyself and Cairn versus Halo have no overlapping included races in the collected run records. Their title success is observable; a direct same-world improvement over the source parent is not measured here.
Some comparisons share no validator, and all have uncontrolled provider/scheduling/model effects. Null telemetry remains unknown, not zero. Whole-sandbox runtime includes parallel tasks and does not directly measure per-task latency. Reported cost is not a reconstructed full provider billing ledger.

Application to future work
For a selected weakness, write the failing scenario and expected behavioral correction before an edit. Identify the active insertion point, supported evidence, normal behavior outside the trigger, state/version invalidation, direct and indirect costs, bounded retries and finishing behavior. Verify guards and recovery boundaries with focused checks, then measure the complete version against its predecessor under comparable budget conditions. Record task gains and regressions, total cost, failures and completion so an aggregate increase cannot hide a lost capability. Keep each experimental change independently attributable. These are an evidence-based working strategy, not proof of future race gains.
