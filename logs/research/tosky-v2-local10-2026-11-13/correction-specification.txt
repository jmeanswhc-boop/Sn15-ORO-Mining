2. PRODUCER/CONSUMER CONTRACT

Generate opaque requirement identifiers from the current runtime ledger and a revision number. Generate evidence identifiers from currently observed fields. Both are local runtime references, not task/product lookup tables. Each evidence reference retains the actual product identity, field scope, field key, JSON value and observation revision in code-owned state.

Illustrative schema, using invented local identifiers:
{
  "revision": 4,
  "item_results": [{
    "item": 1,
    "id": "observed product identity",
    "requirement_results": [{"rid": "r1", "state": "met", "evidence_ids": ["e3"]}]
  }],
  "missing": [],
  "better": []
}

The model selects requirement/evidence IDs and a finite result state. It does not copy full field values, repeat the requirement text as a key, invent new requirement rows or restate numeric/boolean observations. Validate all IDs against the exact current snapshot and the assigned item. A withdrawn requirement, changed record, different product or earlier revision invalidates dependent references.

Global constraints remain typed fields from the v4 task state: budget and scope, quantities, availability policy, message ceiling, step ceiling and explicit procedure duties. They are not inserted as strings into product requirements by the corrective review. The model cannot turn indifference, an aesthetic hint or an irrelevant catalog property into a new live need. Preserve the existing v4 product-coverage audit separately; do not gate all product corrections on the v2 all-purpose completeness certificate.

No correctness decision depends on a global complete/source_complete confidence flag. Derive usable status from coverage of actual active requirement IDs, grounded evidence, the selected objective and separately checked obligations. A response that omits an active ID is unknown/invalid; a response that adds an ID is invalid. Neither condition proves that the product fails.

Do not rely on an unverified provider-specific response-format feature. Enforce the contract locally, with a bounded format-only correction route.

3. ERROR CLASSIFICATION AND ROUTING

REVIEW_FORMAT_ERROR:
Examples: assignments[0].evidence is prose; an evidence field has a wrong JSON type; a requirement reference is absent, extra or stale. Return the exact field path, received type/value category and expected shape. Preserve the current basket and source facts. Route to a format-only decision using the already observed state. Do not search, reread, remove a product or cache a negative cart verdict because of this error.

MISSING_OBSERVATION:
Name the exact active requirement and record/field whose absence affects the selected decision. A supplied schema must permit the proposed read/search action. For pick=any, an unknown alternative does not create a missing observation when the selected item already meets the actual requirements. Do not require warranty, shipping, aesthetics or ranking unless the task has made it binding.

VERIFIED_MISMATCH:
Requires a real active requirement, matching entity/scope and grounded conflicting evidence. Route the specific product/constraint fault to the shopping planner. Preserve legitimate rejection of wrong stock, quantity, price, product type, unresolved references and unmet procedures. A free-form negative opinion without a grounded active requirement does not become a verified mismatch.

REVIEW_UNAVAILABLE:
Transport failure, missing result or exhausted local correction opportunity. Preserve unknown. It cannot erase an existing valid negative review, manufacture a positive match, or become a new permanent negative review. Existing v4 safeguards and finalization remain in force; do not add a universal new veto from this overlay.

LOCAL_REQUEST_TOO_LARGE:
Record available funds, protected funds and the refused packet's size. Switch to a bounded current-decision packet if it is admissible. Keep the financial cap, physical-attempt accounting and 402 stop. A local oversized request is not proof of global account exhaustion or an infeasible shopping task.

4. CACHE AND PROGRESS

Cache verified results by source revision, active requirement IDs, selected item/quantity and the relevant observation revisions. Invalid or unavailable responses do not enter the boolean negative-verdict map. A real change invalidates dependent results; an unchanged transient formatting error does not invalidate observed product facts.

Count progress as new relevant evidence, a changed binding, a corrected protocol result or a real cart/procedure transition. A step-number increment alone is insufficient: reading the same unchanged record again must not indefinitely renew the repair loop. Each repair must name the condition it is expected to change.
