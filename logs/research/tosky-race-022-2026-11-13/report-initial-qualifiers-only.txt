2. What can and cannot be concluded about cost and time

Both Tosky race runs are included SUCCESS runs. Each reports 90 completed outcomes and no run-level failure reason. Only two inference failures were reported across 3,277 requests. This weighs against a catastrophic run-wide provider outage or an unfinished run as the main explanation. It does NOT exclude a locally denied inference, an internal guard forcing a decline, an empty response, a per-episode timeout, or an error caught by the agent. Completed is an outcome label, not proof of a correct purchase.

The two public qualifying runs cost $0.51601723 and $0.51498625, with actual sandbox durations 88.4 and 104.0 seconds. Mean: $0.51550 and 96.2 seconds. CHIDORI's published qualifying runs averaged $0.71452 and 113.55 seconds. Tosky's observed qualifier cost was 27.85% lower, despite making 833 versus 757 inference requests across the two runs. Requests alone cannot estimate billing.

The local source sets AGENT_USD_LIMIT=.035 per episode and reserves .010 for procedures. Across 90 episodes that is a nominal $3.15 allocation per validator run. It is an internal admission model based on serialized prompt bytes, estimated token/pricing envelopes, reported cost and uncertainty reservations; it is not the provider's billed total or proof that the race cost stayed below $5. A conservative quote can deny a useful late call while actual billed room remains, and no public internal logs currently quantify how often that happened.

ORO's documented $5 scoped-key cap applies PER EVALUATION RUN, not once to both validators combined. Two independent race runs can therefore be billed separately. No OpenRouter credentials were accessed; no paid inference, practice verification, submission or agent execution was performed in this analysis.

3. Exact public qualifying failures and matched controls

These are confirmed qualifying diagnoses and observations. They are not a substitute for the unreleased race task breakdown.

A. Dining set, t-20fcb00ff0 — undiscovered needs, both Tosky runs

Both traces finish in nine steps with a purchase. All three allowed shopper messages are spent: first seats, then style/shape/material, then a long list of overlapping topics. Every reply expresses indifference. ORO labels both episodes needs_not_found. CHIDORI fails both controls the same way in nine steps.

Confirmed: a completed purchase occurred without discovering a required shopper need; the message budget was used. The hidden required property's identity and value are not exposed by these failures. It would be unsound to assert that a particular seat count, color or material was the missing requirement. The repeated long lists show questioning coverage is not equivalent to successful disclosure.

B. Single-pack cola, t-3254025544 — stated request not met, both runs

The request explicitly asks for the single pack type, one can/bottle, excluding multipacks. Both Tosky runs buy p-49ac068a9d5b. The viewed record has pack size 1, options 1 x 320ml, and can packaging, but does not supply the requested pack_type field. ORO reports request_not_met. CHIDORI buys the same listing and fails both controls.

Strong candidate mechanism: treating evidence for pack size or packaging as if it settled a distinct requested pack-type property. However, the public grader does not expose which check failed. A one-can listing may look semantically adequate to a human. The trace supports an attribute-evidence mismatch as the investigation target, not a claim that the private check was read. A different public control exposes p-06d9cce41aa6 with pack_type=single and a successful purchase; no such listing ID belongs in production logic.

C. Sugar-free cola, t-6fd2a792df — undiscovered needs, both Tosky runs

In one trace, messages 1 and 3 describe shelf options while only the middle message asks about packaging type. In the other trace the questions cover packaging type and a bundle of other properties, followed by an informational message. Both end in a purchase with needs_not_found.

The matched passing CHIDORI control asks about pack size first; the shopper explicitly replies with pack type=single. It then buys the listing whose record actually supplies pack_type=single and passes. CHIDORI's other control fails. The public evidence supports a concrete missed-disclosure opportunity and message-allocation weakness. It does not support a permanent hardcoded preference for that property on other tasks.

D. Prescription glasses, t-fc0b16b797 — explicit property/range mismatch, both runs

The request requires power lenses up to +/-6.00, permits clear or multicolor lens color, and asks for the cheapest fitting option. Both Tosky failures buy p-749e25fece7c at price 52. The inspected record exposes power_lenses=0.1-0.4, power=0.1, and multicolor lens color. It supplies no support for the requested +/-6.00 range. Much of the later work repeats clear-color searches; the cart remains the unsuitable product and checkout succeeds operationally but scores zero. CHIDORI fails both controls too.

Confirmed visible problem: satisfying an allowed color and low price was not enough to establish the independent optical-power requirement. The exact internal review response and any budget denial are unavailable, so the trace does not identify whether the reviewer approved the wrong thing, never returned a usable answer, or was bypassed. The code permits those to be different mechanisms.

E. Polyester sweater/cardigan, t-e622afe641 — false decline after reply interpretation, one Tosky run

Step 10 already opens p-5a1a59c0c2d9: in the supplied Women's Sweaters and Cardigans category, material polyester, neckline boat neck, price 1611 under the 3250 ceiling. Step 16 gives the shopper response specifying boat neck. Subsequent searches contain the framing text closed, with boat neck and closed neckline. They return zero results; a targeted boat-neck search finds the known listing again at steps 19-20. Nevertheless the episode declines at step 33 and scores request_not_met.

Tosky's other run receives the same shopper wording, buys that same listing, and passes at step 19. Both CHIDORI controls buy it and pass. This is unusually strong paired public evidence: the listing can pass this task, and the bad branch was not caused by that listing being absent or over budget. The trace strongly supports an unstable interpretation/normalization branch; internal model replies are not public, so the exact text stored in the ledger is an inference from the emitted searches, not a directly observed variable.

F. Slip-on footwear, t-fa3dff6e42 — narrative contamination and false decline, one Tosky run

The failed run immediately searches slip-on stage performance, even though stage-exit wording in the public request is narrative context. It repeatedly concentrates on stage-performance footwear with pearl-buckle descriptions, adds/removes such an item, continues several closely related queries, and declines at step 28. A search token is also populated with a category-looking string and receives an invalid-article response. A broad slip-on query had reported 630 matches; this is not itself proof a valid item exists.

The actual passing Tosky run buys p-ee497ff6a7cc and passes at step 15; a CHIDORI control passes with that same listing. CHIDORI's other control also fails this task. This proves a valid outcome exists and supports a contaminated intent/search branch rather than global catalog impossibility. It does not prove which internal method first added stage performance or which v4 change caused the branch.

Across the two Tosky qualifying runs: 50 passes, four needs_not_found failures and six request_not_met failures. Four task IDs fail consistently in both runs; two additional task IDs fail once. Three persistent failures are also persistent in CHIDORI. No qualifying failure is attributed by ORO to infrastructure, process_requirements, optimality or did_not_finish in this observed set. The single reported category is not an exhaustive list of all defects in an episode.

4. The most consequential code weakness supported by these controls

The central weakness is the reliability of the binding requirement state consumed by search, questioning and cart review. A well-formed model answer can still have the wrong property, scope, polarity, value, unit or narrative interpretation. Once that answer is admitted, later layers can faithfully optimize against the wrong requirement.

Relevant local v4 code:
- E1.read_brief, line 1821: initial free-text request -> model-generated musts/name/shelf/roles.
- REPLY_PROMPT, line 317: already tells the model to strip surrounding answer framing. The observed framing leak therefore is not explained by the complete absence of such an instruction.
- E6.read_answers, line 4632, and E6.fold_reading, line 4602: interpretation -> binding told needs. fold_reading accepts a nonempty need string and appends it without source-span or semantic admission checks.
- E1.live_of, line 2031: combines musts and told needs minus dropped strings; dependent stages consume that shared state.
- E5.value_words, line 3899: reuses the free-text value portion in searches.
- G5B.lacks_values, line 8822: lexical evidence checks; token presence/absence cannot certify units, ranges or property identity.
- ScopedControls.ensure_source_coverage, line 10947: explicitly preserves the existing ledger and reports omitted constraints. It can add supported omissions, but cannot remove an invented initial constraint or replace a mis-normalized existing value. It can also leave a bad old value beside a correct addition.
- G5A.cart_check, line 8677: returns an empty issue string if no usable review object is returned. ScopedControls.terminal_recovery_hold, line 11271, requires a current positive review in fallback/recovery, while the ordinary path does not get the same unconditional positive-review guarantee. This is a verified code risk, not a proven explanation for any particular hidden race episode. Simply making every unavailable review block checkout could create a new non-finishing regression.

AST comparison confirms the initial brief reader, reply reader, reply folding, value-word extraction, question planning and lexical missing-value helper are unchanged from the archived CHIDORI implementation. AST equality establishes implementation identity for these methods, not proof that their runtime outputs are identical. The observed shared failures are consistent with those inherited weaknesses surviving v4's additional recovery/procedure/audit layers.

5. A scoped next-step plan, with evidence requirements

First complete today's diagnosis after ORO releases the details: collect every expected/persisted race episode for both included runs and the comparator, verify counts and diagnostics availability, join by task ID and validator, inspect the first observable wrong decision, and separate intent, disclosure, evidence/comparison, recovery, time and inference-limit failures. Race losses must not be allocated to today's qualifier categories by guesswork.

Then prioritize the constraint intake/revision boundary shared by initial request interpretation and shopper-response interpretation. Represent the source property, allowed/excluded values or range, unit, item scope, source quotation and later revision explicitly. Validation must support correcting or rejecting unsupported existing interpretations; adding more constraints alone does not cure a poisoned one. Uncertain equivalence between related property names must remain uncertain. Do not add lists of benchmark product IDs, fixed attribute/value registries, reply phrases, or accepted answers to production code.

Start with the strongest bounded observation: frame leakage in a shopper value followed by false infeasibility. Verify that the successful boat-neck branch still works, its changed/retracted forms still work, unrelated properties remain separate, and source framing is not sent as a literal search value. Also preserve alternatives, negations, numeric units, quantities and reference requirements. This is a narrower and more testable first update than changing every search/review mechanism together.

Next evaluate interview allocation using successful and failing controls, with procedure-message obligations preserved. A topic is valuable when it can resolve a real unknown, not merely because it is a frequent attribute. Keep semantic aliases tied to their item/property scope and avoid repeated information messages that exhaust disclosure opportunities.

Keep the current budget limit until actual race billing and local denial traces are released. Prefer reusing validated state and bounded contradiction-triggered repair over adding a model call to every stage. Measure paired gains AND losses, correct terminal decisions, provider errors, local denials, cost per correct task and wall time before asserting improvement. Passing offline validation does not establish a race-score gain or guarantee no regression.
